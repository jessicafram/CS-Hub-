Módulo 3: Modelagem de Banco de Dados

Relações many-to-many, pivot tables e integridade referencial.

Agora que entendemos:

  • o problema dos sistemas de pagamento (Módulo 1)
  • a arquitetura da aplicação (Módulo 2)

precisamos entender como os dados são armazenados corretamente no banco.

A pergunta central deste módulo é:
Como modelar dados de forma consistente em um sistema financeiro?

Essa pergunta é crítica porque erros de modelagem podem causar inconsistências financeiras.

1. O papel do banco de dados

O banco de dados é responsável por armazenar:

  • usuários
  • produtos
  • transações
  • relacionamentos entre entidades

No seu projeto você utilizou: MySQL. Esse tipo de banco segue o modelo relacional.

2. O modelo relacional

O modelo relacional foi criado por: Edgar F. Codd. Ele organiza dados em tabelas relacionadas entre si.

Exemplo simples:

  • users
  • products
  • transactions

Cada tabela possui: linhas → registros e colunas → atributos.

id name price
1 Camisa 50
2 Tênis 200

3. Entidades principais do seu sistema

Seu banco possui as seguintes entidades principais:

  • User
  • Client
  • Product
  • Transaction
  • TransactionProduct
  • Gateway

Representação simplificada:
User -> Transaction -> TransactionProduct <- Product

Cada entidade representa um conceito do domínio do sistema.

4. Entidade Product

Tabela: products
Representa: itens que podem ser comprados

Campo Significado
id identificador do produto
name nome
price preço
created_at data de criação

No seu código isso aparece como: Product (TypeScript)

5. Entidade Transaction

Tabela: transactions
Representa: uma compra realizada pelo usuário

Campo Significado
id identificador da transação
user_id usuário que comprou
amount valor total
gateway gateway usado
status estado da transação
external_id id no gateway

Essa entidade representa o evento financeiro principal do sistema.

6. O problema do carrinho de compras

Imagine uma compra simples. Cliente compra: Produto A, Produto B, Produto C. Uma transação precisa armazenar vários produtos.

Agora imagine o contrário. Um produto pode aparecer em várias transações.

Temos então uma relação: muitos para muitos (many-to-many).

7. Relacionamento Many-to-Many

No modelo relacional não podemos conectar duas tabelas many-to-many diretamente. Precisamos criar uma tabela intermediária.

No seu sistema essa tabela é: transaction_products. Essa tabela é chamada de: pivot table.

8. Estrutura da tabela transaction_products

Essa tabela contém:

transaction_id product_id quantity
1 10 2
1 15 1

Isso significa: Transaction 1 comprou 2 unidades do produto 10 e 1 unidade do produto 15.

9. Por que não salvar um JSON com os produtos?

Uma pergunta muito comum em entrevistas é: Por que você não salvou os produtos dentro de um campo JSON na tabela transactions?

JSON 
// Exemplo de abordagem errada em JSON:
{
  "products": [
    { "id": 10, "quantity": 2 },
    { "id": 15, "quantity": 1 }
  ]
}

Problemas dessa abordagem:

  • não permite integridade referencial
  • consultas ficam difíceis
  • índices são limitados
  • dados ficam inconsistentes

Com tabela relacional você pode fazer consultas como:

SQL 
SELECT product_id, SUM(quantity) 
FROM transaction_products 
GROUP BY product_id;

Isso permite responder perguntas como: qual produto vendeu mais?

10. Integridade referencial

Outra vantagem do modelo relacional é o uso de: foreign keys.

Exemplo: transaction_products.product_id → products.id

Isso garante: não existe referência para produto inexistente. Sem isso poderíamos ter: produto_id = 999 mesmo que o produto não exista.

11. Conectando com seu código

Quando uma compra acontece, seu código executa:

TypeScript 
Transaction.create(...)

Depois:

TypeScript 
TransactionProduct.create(...)

Isso cria registros que conectam: transação, produtos e quantidades.

12. Fluxo completo da persistência

Fluxo simplificado: Checkout → Controller → Transaction criada → TransactionProducts criados → Commit no banco.

13. Problema real resolvido

Essa modelagem resolve vários problemas:

  • histórico de compras (qual usuário comprou qual produto?)
  • relatórios financeiros (quanto cada produto vendeu)
  • consistência (produtos sempre válidos)
Simulado Técnica

14. Pergunta de entrevista (Módulo 3)

"Como você modelou o relacionamento entre transações e produtos?"

👉 Clique para revelar a Resposta madura

Como uma transação pode conter vários produtos e um produto pode aparecer em várias transações, modelamos essa relação como many-to-many. Para isso criamos uma tabela intermediária chamada transaction_products, que armazena as chaves estrangeiras da transação e do produto, além da quantidade comprada. Isso permite manter integridade referencial e realizar consultas eficientes no banco.

Conclusão do Módulo 3

Agora você entende: modelo relacional, many-to-many, pivot tables, integridade referencial. E principalmente: por que seu banco foi modelado corretamente.
