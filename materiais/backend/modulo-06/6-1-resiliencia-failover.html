Módulo 6: Resiliência, Failover e Tolerância a Falhas

Como garantir que o seu sistema continue funcionando mesmo quando os serviços externos caem.

Agora que entendemos:

  • arquitetura da aplicação
  • consistência de dados
  • idempotência

precisamos resolver outro problema fundamental dos sistemas distribuídos:

O que acontece quando um serviço externo falha?

Em sistemas de pagamento isso ocorre com frequência.

1. O problema das dependências externas

Seu sistema depende de serviços externos chamados gateways de pagamento.

Arquitetura de Rede 
Cliente
  ↓
Sua API
  ↓
Gateway de pagamento
  ↓
Rede financeira

Mas serviços externos podem falhar. Motivos comuns:

  • instabilidade de rede
  • timeout
  • gateway fora do ar
  • manutenção do provedor
  • sobrecarga do serviço

Se o sistema depender de apenas um gateway: falha do gateway → todo o sistema para. Isso reduz drasticamente a disponibilidade da aplicação.

2. O conceito de resiliência

Em engenharia de sistemas distribuídos, chamamos a capacidade de continuar funcionando mesmo com falhas de: Resiliência.

Resiliência significa: o sistema continua operando mesmo quando partes dele falham. Esse conceito é central em arquiteturas modernas.

Referência famosa: Designing Data-Intensive Applications.

3. Tolerância a falhas

Um sistema tolerante a falhas consegue lidar com problemas como:

  • queda de servidor
  • falha de rede
  • erro de integração

Sem interromper completamente o serviço. Esse conceito é chamado de: Fault Tolerance.

4. Estratégias para lidar com falhas

Existem várias estratégias usadas em sistemas distribuídos. Algumas das principais são: retry, failover, circuit breaker, fallback.

5. Retry

Retry significa simplesmente tentar novamente a mesma operação.

Fluxo: Gateway falha → tentar novamente.

Problema: se o gateway estiver realmente fora do ar retry não resolve. Também pode aumentar a latência da requisição.

6. Failover

Failover significa mudar para um sistema alternativo quando o principal falha.

Fluxo: Gateway 1 → falha → Gateway 2.

Esse é exatamente o padrão que você implementou no seu projeto. Representação:

Fluxo de Sistema 
Payment Service
  ├── Gateway 1 (Falha ❌)
  └── Gateway 2 (Sucesso ✅)

Se o primeiro falhar: PaymentService usa o segundo.

7. Como seu projeto implementa failover

No seu sistema o Payment Service executa a lógica: tentar gateway primário → se falhar → tentar gateway secundário.

Fluxo completo:

  • Cliente envia pagamento
  • Payment Service chama Gateway 1
  • Gateway 1 falha
  • Payment Service chama Gateway 2
  • Gateway 2 processa pagamento

Para o cliente: a operação continua funcionando. Isso aumenta a disponibilidade do sistema.

8. Disponibilidade em sistemas distribuídos

Disponibilidade significa: probabilidade de o sistema estar funcionando. Em sistemas críticos, empresas buscam níveis como: 99.9%, 99.99%, 99.999%. Isso é chamado de: High Availability. Failover é uma técnica fundamental para atingir esse objetivo.

9. Benefícios do failover

O uso de múltiplos gateways traz várias vantagens.

  • continuidade do serviço (falha de um gateway não para o sistema)
  • redução de risco operacional (dependência menor de um único provedor)
  • melhor experiência do usuário (menos pagamentos recusados)

10. Limitações do failover

Embora seja uma boa estratégia, o failover também possui limitações. Exemplo: se ambos gateways falharem. Resultado: pagamento não pode ser processado.

Nesse caso seu sistema retorna: erro seguro para o cliente. Isso é correto para um sistema financeiro.

11. Evoluções possíveis

Sistemas mais avançados adicionam outras estratégias.

Circuit Breaker

Evita continuar chamando um serviço que já está falhando.

  • muitas falhas detectadas
  • circuit breaker abre
  • requisições deixam de ser enviadas

Ferramenta popular: Resilience4j.

Observabilidade

Monitorar o comportamento dos gateways. Ferramentas comuns: Prometheus, Grafana.

12. Conectando com seu projeto

Seu sistema utiliza: PaymentService para resolver três problemas importantes: falha de gateway, indisponibilidade, redundância.

Estratégia aplicada: Failover entre gateways. Fluxo final: Controller → Payment Service → Gateway 1 (falha) → Gateway 2 → Transaction salva.

13. Pergunta de entrevista (Módulo 6)

"Como sua API lida com falhas de gateway?"

👉 Clique para revelar a Resposta madura

O PaymentService implementa uma estratégia de failover entre gateways. Quando uma requisição de pagamento é iniciada, o sistema tenta primeiro o gateway primário. Caso ocorra uma falha, como timeout ou erro de processamento, o serviço automaticamente tenta um gateway secundário. Isso aumenta a disponibilidade do sistema e reduz o impacto de falhas externas.
