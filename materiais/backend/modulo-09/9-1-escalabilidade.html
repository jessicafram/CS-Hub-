Módulo 9: Escalabilidade e Sistemas de Produção

O que precisaria mudar para que essa API suporte milhares de pagamentos por segundo?

Até agora construímos praticamente toda a base de engenharia da sua API:

  • arquitetura em camadas
  • modelagem de banco
  • consistência (ACID)
  • idempotência
  • resiliência
  • segurança
  • tipagem

Agora surge uma pergunta fundamental:
O que precisaria mudar para que essa API suporte milhares de pagamentos por segundo?

Esse é o problema da escalabilidade.

1. O problema da escala

Seu sistema atual funciona assim:

Fluxo Síncrono 
Cliente
  ↓
API
  ↓
Gateway
  ↓
Banco de dados

Esse fluxo é síncrono. Ou seja: cliente espera a resposta da API.

Isso funciona bem em:

  • projetos pequenos
  • baixo volume de requisições

Mas imagine um cenário real: 10.000 requisições por segundo. Agora surgem problemas.

2. Gargalos do sistema

Em sistemas de pagamento existem alguns gargalos comuns.

  • tempo de resposta do gateway: chamada externa pode demorar
  • escrita no banco: muitas transações simultâneas
  • concorrência: muitos usuários ao mesmo tempo

Isso pode causar: lentidão, timeout, sobrecarga.

3. Escala horizontal

Uma das primeiras soluções é escala horizontal. Em vez de um único servidor (API Server), usamos vários:

  • API Server 1
  • API Server 2
  • API Server 3

Na frente deles fica um: Load Balancer.

Load Balancing 
Cliente
  ↓
Load Balancer
  ↓
Múltiplos servidores

Isso permite que o sistema processe mais requisições simultâneas.

4. Processamento assíncrono

Outra estratégia muito usada é processamento assíncrono. Em vez de processar tudo na requisição (Cliente espera o pagamento), podemos usar filas.

Fluxo Assíncrono 
Cliente
  ↓
API recebe requisição
  ↓
coloca evento na fila
  ↓
Worker processa pagamento

Isso desacopla partes do sistema.

Clique nos botões para simular uma enxurrada de acessos simultâneos na sua arquitetura atual (Síncrona) e na arquitetura ideal de produção (Assíncrona).

[Gateway] Tentando processar...

[Workers] 50 Workers consumindo a fila gradativamente...

✅ STATUS: 10.000 pagamentos processados em background sem queda do servidor central!

5. Sistemas de mensageria

Para implementar filas usamos sistemas de mensageria. Alguns exemplos populares: RabbitMQ, Apache Kafka.

Esses sistemas permitem:

  • processamento assíncrono
  • alta escalabilidade
  • tolerância a falhas

6. Workers

Quando usamos filas, adicionamos workers. Workers são processos responsáveis por executar tarefas.

Fila e Worker 
API
  ↓
Fila
  ↓
Worker
  ↓
Gateway

Isso permite processar milhares de pagamentos paralelamente.

7. Rate limiting

Outra proteção importante é limitar requisições. Isso evita ataques ou abusos. Exemplo: 100 requisições por minuto por usuário.

Ferramenta comum em Node: Redis. Redis é usado para armazenar contadores rápidos.

8. Observabilidade

Quando sistemas crescem precisamos monitorá-los. Isso inclui: logs, métricas, alertas.

Ferramentas comuns: Prometheus, Grafana. Isso permite responder perguntas como:

  • quantos pagamentos estão sendo processados?
  • qual gateway está falhando?
  • qual tempo médio de resposta?

9. Circuit breaker

No módulo de resiliência vimos o failover. Mas sistemas de produção também usam Circuit Breaker.

Circuit Breaker 
gateway falha repetidamente
  ↓
circuit breaker abre
  ↓
API para de chamar esse gateway

Isso evita sobrecarregar serviços que já estão falhando.

10. Evolução da arquitetura

Seu sistema atual: Cliente → API → Gateway → Banco

Uma arquitetura de produção poderia evoluir para:

Arquitetura de Produção 
Cliente
  ↓
API
  ↓
Fila
  ↓
Workers
  ↓
Gateway
  ↓
Banco

Isso melhora: escala, resiliência, performance.

11. Conectando com seu projeto

Seu projeto já possui vários elementos importantes para produção:

  • Service Layer
  • Failover de gateway
  • Idempotência
  • Transações ACID
  • RBAC

Esses elementos formam a base de um sistema financeiro robusto.

As evoluções necessárias seriam principalmente: filas, observabilidade, circuit breaker, rate limiting.
