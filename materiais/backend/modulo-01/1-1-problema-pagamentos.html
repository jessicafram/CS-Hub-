O Problema dos Sistemas de Pagamento

Antes de qualquer linha de código, precisamos entender o problema que sistemas de pagamento tentam resolver.[cite: 260] Em engenharia de software, especialmente em backend financeiro, a primeira pergunta não é: como programar?[cite: 261, 262] A pergunta é: qual problema estamos tentando resolver?[cite: 263, 264]

Seu projeto da API de pagamentos é uma resposta para um problema clássico: Como permitir que um cliente pague por produtos de forma confiável, segura e consistente mesmo em um ambiente distribuído como a internet.[cite: 265, 266, 267]

1. O que é uma transação financeira

Uma transação financeira é um evento que representa a movimentação de valor entre duas partes.[cite: 268, 269] Exemplo simples: Cliente compra um produto → valor sai da conta/cartão do cliente → valor vai para o comerciante.[cite: 270, 271, 272, 273]

No seu sistema isso aparece como: Transaction.[cite: 274, 275] No banco de dados da sua API você criou a tabela: transactions.[cite: 276, 277] Ela representa exatamente isso: um evento financeiro.[cite: 278, 279]

Campos comuns em sistemas de pagamento:

[cite: 280]
Campo Significado
transaction_id[cite: 281] identificador da transação[cite: 281]
amount[cite: 281] valor[cite: 281]
status[cite: 281] estado da transação[cite: 281]
gateway[cite: 281] provedor que processou[cite: 281]
external_id[cite: 281] id no gateway[cite: 281]

Isso aparece no seu código quando você cria:[cite: 282]

TypeScript[cite: 283] 
await Transaction.create(...)[cite: 284]

2. O que é um Gateway de Pagamento

Um gateway de pagamento é um sistema externo que conecta sua aplicação ao sistema financeiro.[cite: 285, 286] Ele atua como um intermediário técnico entre seu sistema e as redes bancárias.[cite: 287]

Fluxo simplificado:[cite: 288]
Cliente ↓[cite: 289, 290]
Sua API ↓[cite: 291]
Gateway de pagamento ↓[cite: 292]
Rede financeira ↓[cite: 293]
Banco emissor do cartão[cite: 294]

Gateways famosos incluem: Stripe, PayPal, Adyen.[cite: 295, 296, 297, 298]

Seu projeto simula dois gateways: Gateway 1 e Gateway 2.[cite: 299, 300, 301] E o seu PaymentService faz a comunicação com eles.[cite: 302]

3. Autorização

Quando o cliente tenta pagar, o primeiro passo não é capturar o dinheiro. Primeiro ocorre autorização.[cite: 303, 304, 305]

Autorização significa: o banco verifica se o cliente pode pagar.[cite: 306, 307] Por exemplo: cliente tem limite? cartão é válido? transação é suspeita?[cite: 308, 309, 310, 311]

Resultado possível: approved ou declined.[cite: 312, 313, 314] No seu sistema isso aparece como:[cite: 315]

TypeScript[cite: 316] 
paymentResult.success[cite: 317]

Se for aprovado: segue fluxo.[cite: 318, 319] Se for recusado: erro de pagamento.[cite: 320, 321]

4. Captura

Após a autorização, alguns sistemas fazem a captura do pagamento.[cite: 322, 323] Captura significa: transferir efetivamente o dinheiro.[cite: 324, 325] Fluxo real em muitos sistemas: autorização → captura.[cite: 326, 327, 328] No seu projeto, simplificamos isso para: pagamento aprovado → transação salva.[cite: 329, 330, 331]

5. Chargeback (estorno)

Um chargeback ocorre quando uma transação precisa ser revertida.[cite: 332, 333] Isso pode acontecer quando: cliente solicita estorno, fraude detectada, erro no pagamento.[cite: 334, 335, 336, 337]

No seu código isso aparece em:[cite: 338]

TypeScript[cite: 339] 
async chargeback({params})[cite: 340]

Fluxo: transação encontrada → chamada ao gateway → status atualizado.[cite: 341, 342, 343, 344, 345]
Status final: REFUNDED.[cite: 346, 347]

6. Problema real 1 — Falhas de rede

A internet não é confiável.[cite: 348, 349] Requisições podem falhar por: timeout, queda de conexão, gateway fora do ar.[cite: 350, 351, 352, 353] Exemplo: API chama gateway → gateway não responde.[cite: 354, 355, 356, 357]

Seu sistema resolve isso com: Failover.[cite: 358, 359] Ou seja: Gateway 1 → falha → Gateway 2.[cite: 360, 361, 362, 363] Isso está implementado no seu: PaymentService.[cite: 364, 365]

7. Problema real 2 — Duplicação de pagamento

Imagine o cenário: usuário clica em pagar → internet lenta → ele clica novamente.[cite: 366, 367, 368, 369, 370] Sua API recebe 2 requisições.[cite: 371, 372] Sem proteção isso pode gerar 2 cobranças.[cite: 373, 374]

Seu projeto resolve isso com: Idempotency-Key.[cite: 375, 376] Trecho do seu código:[cite: 377]

TypeScript[cite: 378] 
const idempotencyKey = request.header('Idempotency-Key')[cite: 379]

Se a chave já existir: retorna transação existente.[cite: 380, 381]

8. Problema real 3 — Consistência de dados

Imagine este erro: pagamento aprovado → erro ao salvar no banco.[cite: 382, 383, 384, 385] Resultado: cliente pagou, mas sistema não registrou.[cite: 386, 387, 388] Isso é catastrófico em sistemas financeiros.[cite: 389]

Por isso você usou:[cite: 390]

TypeScript[cite: 391] 
db.transaction()[cite: 392]

Isso garante propriedades chamadas: ACID. Esse conceito será aprofundado no Módulo 4.[cite: 393, 394, 395]

Simulado Técnica 10. Pergunta de entrevista (Módulo 1)

Depois de entender esse módulo, você consegue responder:

"O que é um gateway de pagamento e por que usamos mais de um?"

👉 Clique para revelar a Resposta madura
Um gateway de pagamento é um serviço que intermedia a comunicação entre a aplicação e a rede financeira responsável por autorizar e processar pagamentos. Em sistemas críticos, é comum utilizar mais de um gateway para melhorar a disponibilidade. Caso o gateway principal falhe por problemas de rede ou indisponibilidade, o sistema pode realizar failover para um gateway secundário, garantindo maior resiliência no processamento das transações.
